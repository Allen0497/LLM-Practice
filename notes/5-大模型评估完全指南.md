## 第零章：评估在大模型训练中的位置

```
┌─────────────────────────────────────────────────────────────────────┐
│                     大模型训练完整流程                                │
│                                                                     │
│   ① 预训练（Pre-Training）                                          │
│   ② 续训练（Continual Pre-Training）                                │
│   ③ 指令微调（SFT）                                                 │
│   ④ 偏好对齐（RLHF / DPO / GRPO）                                  │
│   ⑤ 评估（Evaluation）           ← 📍 我们现在在这里！              │
│   │  用"标准化考试"给模型打分，量化模型能力                          │
│   │                                                                 │
│   ⑥ 部署上线                                                        │
└─────────────────────────────────────────────────────────────────────┘
```

**打个比方：**

| 阶段 | 类比 |
|------|------|
| 预训练 | 上学读书 |
| SFT | 岗前培训 |
| 偏好对齐 | 职业素养训练 |
| **评估** | **期末考试 / 入职考核** |
| 部署 | 正式上岗 |

评估不是"训练的一部分"，而是"训练完成后的验收环节"。它回答一个问题：

> **我辛辛苦苦训出来的这个模型，到底行不行？**

## 第一章：为什么要评估？如何评估？

### 1.1 评估的三大用途

1. **选模型**：在多个 checkpoint / 多家开源模型中，选一个最强的
2. **调超参**：训练过程中监控 benchmark 分数，判断训练是否收敛、是否过拟合
3. **对外宣传**：发布模型时公布 MMLU、C-Eval 等分数，让用户了解能力

### 1.2 两种评估范式

| 范式 | 做法 | 优缺点 |
|------|------|--------|
| **生成式评估** | 让模型自由生成文本，然后判断内容是否正确（如翻译、摘要） | 贴近真实使用，但难以自动打分 |
| **判别式评估**（本脚本） | 给模型选择题，看它选哪个 | 容易自动化、可复现、速度快 |

判别式评估还可以细分为：

- **Perplexity 评估**：看模型对正确选项整体的"困惑度"（概率越高越好）
- **Logits 打分**（本脚本使用）：只看 A/B/C/D 四个 token 的预测概率

### 1.3 一句话概括本脚本的评估流程

```
   题目 + 5个示范题（5-shot）
           ↓
       送进模型
           ↓
   取最后位置的 logits
           ↓
只看 " A"/" B"/" C"/" D" 4 个 token 的概率
           ↓
     argmax 得到预测答案
           ↓
      与标准答案对比
```

## 第二章：MMLU 基准介绍

### 2.1 什么是 MMLU？

**MMLU**（Massive Multitask Language Understanding）是目前最流行的大模型通用能力评测基准之一。

- 出处：加州大学伯克利分校 2020 年提出
- 规模：57 个学科，约 15,000 道多选题
- 覆盖：从小学数学到研究生级别的法律、医学、哲学
- 题型：每题 4 个选项（ABCD），只有一个正确答案

### 2.2 57 个学科分 4 大类

```
┌─────────────────────────────────────────────────────────────┐
│  MMLU 四大类别                                              │
├─────────────────────────────────────────────────────────────┤
│  STEM（19科）       │  科学、技术、工程、数学                │
│                     │  如：抽象代数、大学物理、机器学习        │
├─────────────────────────────────────────────────────────────┤
│  Humanities（13科）│  人文                                   │
│                     │  如：世界史、国际法、哲学、道德场景       │
├─────────────────────────────────────────────────────────────┤
│  Social（12科）     │  社会科学                               │
│                     │  如：心理学、经济学、社会学              │
├─────────────────────────────────────────────────────────────┤
│  Other（13科）      │  其他专业领域                           │
│                     │  如：医学、管理、营销、病毒学            │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 数据文件结构

MMLU 每个学科有两份 csv 文件：

```
eval_data/
├── dev/                          ← 开发集（每学科约 5 题，用于 few-shot 示范）
│   ├── abstract_algebra_dev.csv
│   ├── machine_learning_dev.csv
│   └── ...
└── test/                         ← 测试集（实际评测）
    ├── abstract_algebra_test.csv
    ├── machine_learning_test.csv
    └── ...
```

每行数据格式：

| question | A | B | C | D | answer |
|----------|---|---|---|---|--------|
| What is 2+2? | 3 | 4 | 5 | 6 | B |

### 2.4 Qwen-7B 在 MMLU 上的参考分数

| 模型 | MMLU |
|------|------|
| GPT-4 | ~86% |
| Qwen2.5-7B-Instruct | ~74% |
| LLaMA-3-8B | ~66% |
| 随机猜（4选1） | 25% |

如果你的模型跑出来只有 25% 左右，说明它基本是"瞎猜"。

## 第三章：Few-shot Learning（少样本学习）

### 3.1 为什么要用 few-shot？

假设你直接问一个基座模型：

```
Question: What is 2+2?
A. 3
B. 4
C. 5
D. 6
Answer:
```

**基座模型没学过"选择题格式"**，它可能会输出：

```
Answer: Well, mathematically speaking, two plus two equals...
```

它没有意识到"下一个 token 应该是 A/B/C/D 其中之一"。

### 3.2 Few-shot 的做法

在真正的题目前，先塞 **k 道做好的示范题**（带答案），告诉模型"这种题就该这么答"：

```
The following are multiple choice questions (with answers) about machine learning.

Question: 示范题 1
A. ...
B. ...
Answer: A

Question: 示范题 2
A. ...
B. ...
Answer: C

... （共 5 道示范题）

Question: 真正要答的题
A. ...
B. ...
Answer:       ← 让模型在这里预测
```

MMLU 的标准评测使用 **5-shot**（k=5）。示范题来自 dev 集，不会跟 test 集重叠。

### 3.3 Few-shot 的本质

Few-shot 没有更新模型参数，它只是在 **prompt 里提供上下文**，利用大模型的 **in-context learning**（上下文学习）能力。

> "给你看几个例子，你就会了" —— 这是大模型最神奇的能力之一。

## 第四章：评估的核心技巧 —— Logits 打分法

### 4.1 问题：怎么把"文本生成"变成"客观评分"？

如果让模型自己生成文本，它可能输出：

- `"B"` ← 干净利落
- `" B. The correct answer is B"` ← 还附带解释
- `" Let me think... the answer should be B"` ← 思维链
- `"答案是B"` ← 中文回答

**每种输出都需要不同的解析规则**，非常麻烦，而且可能判错。

### 4.2 解决方案：直接看 logits

与其让模型生成，不如直接看它"**最可能输出什么 token**"。

```python
# 1. 把 prompt 送进模型
outputs = model(input_ids)          # [batch, seq_len, vocab_size]

# 2. 只取最后一个位置的 logits（即"Answer:"之后要预测的 token）
logits = outputs[:, -1, :]          # [batch, vocab_size]

# 3. 只看 " A"/" B"/" C"/" D" 四个 token 的分数
#    vocab 里其他 token（比如 "Let"、"The"）的概率直接忽略
choices_ids = [id_of(" A"), id_of(" B"), id_of(" C"), id_of(" D")]
probs = softmax(logits[:, choices_ids])   # [batch, 4]

# 4. argmax 取最大的那个
pred = argmax(probs)                # 0/1/2/3 → A/B/C/D
```

### 4.3 为什么是" A"（带空格）而不是"A"？

这是一个非常容易踩坑的细节。

Prompt 的结尾是：
```
...Answer:
```

模型要预测的下一个 token，通常会**带一个前导空格**：

```
"Answer:" → " A"         ✅ 这是模型实际预测的 token
"Answer:" → "A"          ❌ 这通常不是模型预测的（因为冒号后习惯有空格）
```

所以代码里是：

```python
tokenizer(" A")["input_ids"]    # 注意前面的空格！
```

> 💡 **小提示**：不同 tokenizer 的行为可能不一致。最严谨的做法是打印 `tokenizer(" A")` 和 `tokenizer("A")`，看看到底是不是不同的 token ID。

### 4.4 为什么再 softmax 一次？

```python
softval = logits.gather(1, choices_ids).softmax(1)
```

- 第一次 softmax（在 `get_logits` 里）是对**整个 vocab（~15 万 token）** 做归一化
- 第二次 softmax 只对 **A/B/C/D 4 个 token** 做归一化，得到"在必须从 4 个里选的前提下，每个选项的概率"

这样得到的 `[P(A), P(B), P(C), P(D)]` 相加为 1，便于分析。

## 第五章：左侧 Padding 与 eval 模式 —— 评估的两个关键细节

### 5.1 为什么评估要用 `padding_side='left'`？

因果语言模型（Causal LM）只能"向后看"，它预测的永远是**序列最后一个 token 之后**的下一个 token。

**右侧 padding 的问题：**

```
Prompt:   [Q u e s t i o n . . . A n s w e r :]
加 pad:   [Q u e s t i o n . . . A n s w e r : <pad> <pad> <pad>]
                                                          ↑
                                    模型预测这里的下一个 token，结果是基于 pad 的！
```

**左侧 padding 的做法：**

```
加 pad:   [<pad> <pad> <pad> Q u e s t i o n . . . A n s w e r :]
                                                                ↑
                                              模型预测这里的下一个 token，正确！
```

> 💡 **记住**：训练时可以右侧 padding（因为有 label mask），但**推理/评估必须左侧 padding**。

### 5.2 为什么要用 `model.eval()`？

```python
model = AutoModelForCausalLM.from_pretrained(...).eval()
```

`eval()` 切换到评估模式，主要影响：

| 层 | train 模式 | eval 模式 |
|------|------------|-----------|
| Dropout | 随机丢弃神经元 | 全部保留 |
| BatchNorm | 用 batch 统计量 | 用训练时累积的统计量 |
| LayerNorm | 不变 | 不变 |

大模型（Transformer）里主要是 **Dropout** 的影响。不切 eval 模式的话，每次评估结果都会略有不同（因为 dropout 是随机的），**无法复现**。

### 5.3 `@torch.no_grad()` 装饰器

```python
@torch.no_grad()
def eval_subject(...):
    ...
```

告诉 PyTorch"这个函数里不需要反向传播"，于是：

- 不保存中间激活值 → **省大量显存**
- 不构建计算图 → **速度更快**

评估只做前向，所以必加。

## 第六章：代码逐行对照解读

### 6.1 整体结构

```
main(args)
  ├─ load_models_tokenizer()       # 加载模型 + tokenizer（eval 模式、左侧 padding）
  ├─ for subject in 57 个学科：
  │    ├─ 读 dev.csv（few-shot 示例）
  │    ├─ 读 test.csv（测试题）
  │    └─ eval_subject()
  │         ├─ generate_few_shot_prompt()   # 构造 5 个示范题
  │         ├─ for batch in test_df：
  │         │    ├─ format_example(include_answer=False)  # 测试题
  │         │    ├─ get_logits()            # 前向，取最后位置 logits
  │         │    ├─ gather + softmax        # 只保留 ABCD 概率
  │         │    └─ argmax → 预测答案
  │         └─ 存 csv 结果
  └─ cal_mmlu()                    # 统计 4 大类的准确率
```

### 6.2 关键代码片段解读

**① Prompt 构造**（`format_example`，第 74-107 行）

```python
example = "Question: " + line["question"]
for choice in choices:          # ["A", "B", "C", "D"]
    example += f'\n{choice}. {line[f"{choice}"]}'
if include_answer:
    example += "\nAnswer: " + line["answer"] + "\n\n"
else:
    example += "\nAnswer:"      # 留白，让模型预测
```

**② 四选项 token ID**（`eval_subject`，第 223-226 行）

```python
choices_ids = torch.tensor(
    tokenizer(" A")["input_ids"] + tokenizer(" B")["input_ids"] +
    tokenizer(" C")["input_ids"] + tokenizer(" D")["input_ids"]
).unsqueeze(0).to(model.device)
# 形状：[1, 4]，内容如 [[464, 465, 466, 467]]
```

**③ 只挑 4 个选项的概率**（第 251 行）

```python
softval = logits.gather(1, choices_ids.expand(logits.size(0), -1)).softmax(1)
#         ↑ 从 vocab_size 里挑出 4 个位置                    ↑ 只在 4 个之间归一化
```

`gather` 的作用：沿着 `dim=1`（vocab 维度），按 `choices_ids` 指定的索引挑出对应概率。

**④ 预测答案**（第 264 行）

```python
pred = {0: "A", 1: "B", 2: "C", 3: "D"}[np.argmax(probs[i])]
```

**⑤ 长序列截断**（第 166-167 行）

```python
if input_ids.shape[1] > args.max_seq_len:
    input_ids = input_ids[:, input_ids.shape[1] - args.max_seq_len + 1:]
#                         ↑ 从前面截，保留末尾的题目部分
```

Few-shot + 长题目可能超过模型最大长度（比如 2048），这时要**从头部截断**，因为：

- 前面是示范题（可以丢一两个）
- 后面是真正要答的题（不能丢！）


## 第七章：其他常见评估基准一览

MMLU 只是大模型评估的冰山一角。下面列举几个常见基准，建议后续逐个了解：

| 基准 | 侧重 | 题型 |
|------|------|------|

| **CMMLU** | 中文综合，侧重中国国情 | 4 选 1 多选 |

| **BBH** | 推理挑战（Big-Bench Hard） | 多种题型 |

| **HellaSwag** | 常识推理 | 4 选 1 |

- 通用基座模型 → **MMLU / C-Eval / CMMLU**

- SFT/对齐后的对话模型 → **MT-Bench / AlpacaEval / IFEval**
- 想全面评估 → **OpenCompass / lm-evaluation-harness** 等评测框架（打包了几十个基准）

## 附录：常见问题

### Q1：我的模型 MMLU 只有 25%，是不是坏了？

4 选 1 瞎猜的期望是 25%。如果你的模型在 25% 附近：

- 小模型（<1B）本身在 MMLU 上就表现很差，属正常
- 预训练数据量/质量不足，模型还没学到知识
- 检查 prompt 格式是否正确（尤其是 `" A"` 带空格的坑）
- 检查是否忘了 `padding_side='left'`

### Q2：为什么不让模型生成"A"/"B"字符串，而要取 logits？

两个原因：
1. **可解析性**：logits 一定能 argmax 出一个答案，生成可能输出无法解析的文本
2. **速度**：logits 只做一次前向；生成要自回归地吐出多个 token

### Q3：Few-shot 的 k 为什么是 5？

历史惯例。MMLU 原论文就是用的 5-shot，大家都跟着用以便对比。k 越大效果通常越好（到一定程度饱和），但会消耗更多上下文长度。

### Q4：能不能加 CoT（思维链）？

能，但需要改评估方式：
- Prompt 改成"Let's think step by step"
- 不再取 logits，而是让模型自由生成
- 从生成文本里解析最终答案（如匹配 `"answer is (A)"` 这种 pattern）

对数学/推理类任务（GSM8K、MATH）CoT 效果非常显著，但对纯知识题（MMLU）提升有限。

### Q5：评估结果为什么每次都一样？

因为：
- `model.eval()` 关闭了 dropout（确定性）
- 本脚本不做采样，只做 argmax（确定性）
- 数据读取顺序固定

这正是判别式评估的优势：**完全可复现**。

### Q6：评估一次要多久？

MMLU 共约 14,000 道题，一张 A100 上：
- batch_size=1：几小时
- batch_size=8：约 30-60 分钟
- 更大 batch：看显存

可以先跑 1-2 个学科测通流程，再跑全量。

### Q7：评估分数高就是好模型吗？

不一定。Benchmark 分数反映的是"做题能力"，而真实使用体验取决于：
- 对话流畅度
- 指令遵循
- 幻觉率
- 多轮一致性
- 中文语感（如果针对中文场景）

Benchmark 只是一个维度。真正发布模型前，务必做**人工评测**和**MT-Bench / Arena** 这类对话评测。

### Q8：怎么防止"刷榜"？

业界公开的真问题：很多模型在训练数据里混入了 benchmark 测试集（数据污染），分数虚高。防范手段：

- 做**新鲜基准**（如 LiveBench，每月更新题目）
- 用**私有测试集**（不公开题目）
- 看**对战类评测**（Chatbot Arena）而非静态 benchmark

## 🎓 小结

至此，大模型训练的完整闭环（预训练 → SFT → 评估）就串起来了。回顾一下评估的关键要点：

1. **评估的本质**：用标准化试题量化模型能力
2. **MMLU**：57 学科的 4 选 1 多选题，最主流的英文通用基准
3. **Few-shot**：在 prompt 里放 5 个示范题，利用上下文学习
4. **Logits 打分法**：不让模型生成，直接看 `" A"/" B"/" C"/" D"` 四个 token 的预测概率，argmax 得答案
5. **两个关键细节**：`padding_side='left'` + `model.eval()` + `@torch.no_grad()`
6. **评估要多样**：MMLU 之外还有 C-Eval、GSM8K、HumanEval、MT-Bench 等，不同模型用途选不同基准

- **LLM-as-Judge**（用大模型当裁判）—— 对应 `qwen_judge.py`
- **知识蒸馏**（用大模型教小模型）—— 对应 `qwen_distill.py`
