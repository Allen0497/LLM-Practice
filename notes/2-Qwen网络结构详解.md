## 第一章：Qwen2.5-0.5B 整体网络结构

### 1.1 架构类型

Qwen2.5-0.5B 使用的是 **Decoder-Only Transformer**，这是目前几乎所有主流大模型（GPT、LLaMA、DeepSeek、Qwen）共用的架构。

对应代码中的加载方式：

```python
# qwen_pt.py 中从零初始化
config = AutoConfig.from_pretrained("models/Qwen2.5-0.5B")
model = AutoModelForCausalLM.from_config(config)
```

### 1.2 config.json —— 模型的建筑图纸

`models/Qwen2.5-0.5B/config.json` 定义了所有架构参数：

```json
{
  "hidden_size": 896,
  "num_hidden_layers": 24,
  "num_attention_heads": 14,
  "num_key_value_heads": 2,
  "intermediate_size": 4864,
  "vocab_size": 151936,
  "max_position_embeddings": 32768,
  "hidden_act": "silu",
  "rope_theta": 1000000.0,
  "rms_norm_eps": 1e-06,
  "tie_word_embeddings": true
}
```

### 1.3 完整网络结构图

```
输入: token IDs [batch_size, seq_len]
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│  Embedding 层                                            │
│  vocab_size=151936 → hidden_size=896                     │
│  把每个 token ID 映射成一个 896 维的向量                    │
│  （15万个词，每个词用896个数字表示）                         │
└───────────────────────┬─────────────────────────────────┘
                        │ [batch, seq_len, 896]
                        ▼
┌─────────────────────────────────────────────────────────┐
│  Transformer Decoder Block × 24 层                       │
│  ┌───────────────────────────────────────────────────┐  │
│  │ ① RMSNorm（Pre-Norm）                             │  │
│  │   rms_norm_eps=1e-6                               │  │
│  ├───────────────────────────────────────────────────┤  │
│  │ ② 自注意力（Grouped-Query Attention, GQA）         │  │
│  │   Q: 14个头 × 64维                                │  │
│  │   K:  2个头 × 64维  ← 7个Q头共享1个KV头            │  │
│  │   V:  2个头 × 64维                                │  │
│  │   位置编码: RoPE (rope_theta=1000000)             │  │
│  ├───────────────────────────────────────────────────┤  │
│  │ ③ 残差连接: output = input + attention_output     │  │
│  ├───────────────────────────────────────────────────┤  │
│  │ ④ RMSNorm                                        │  │
│  ├───────────────────────────────────────────────────┤  │
│  │ ⑤ SwiGLU FFN                                     │  │
│  │   gate_proj:  896 → 4864  (SiLU激活)              │  │
│  │   up_proj:    896 → 4864                          │  │
│  │   down_proj: 4864 → 896                           │  │
│  ├───────────────────────────────────────────────────┤  │
│  │ ⑥ 残差连接: output = input + ffn_output           │  │
│  └───────────────────────────────────────────────────┘  │
│              ↑ 重复 24 次                                │
└───────────────────────┬─────────────────────────────────┘
                        │ [batch, seq_len, 896]
                        ▼
┌─────────────────────────────────────────────────────────┐
│  RMSNorm（最终归一化）                                    │
└───────────────────────┬─────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────┐
│  LM Head（语言模型头）                                    │
│  896 → 151936                                            │
│  tie_word_embeddings=true → 与 Embedding 层共享权重        │
│  输出每个位置上"下一个token是谁"的概率分布                    │
└─────────────────────────────────────────────────────────┘
        │
        ▼
输出: logits [batch_size, seq_len, 151936]
  → 交叉熵 loss → 反向传播 → 更新参数
```

### 1.4 关键设计解释

**GQA（Grouped-Query Attention）**

普通多头注意力每个 Q 头配一个 KV 头（14Q:14KV）。GQA 让多个 Q 头共享一组 KV（14Q:2KV，每 7 个 Q 头共享 1 个 KV 头），推理时 KV Cache 显存减少 7 倍，速度更快，效果几乎不损失。

**RoPE（旋转位置编码）**

不像早期 Transformer 用绝对位置编码，RoPE 把位置信息编码到注意力的 Q/K 向量中，通过旋转矩阵实现。`rope_theta=1000000` 这个很大的值让模型能处理超长序列（最大 32768 token）。

**tie_word_embeddings=true**

输入 Embedding 层和输出 LM Head 共享同一个权重矩阵（151936×896），节省约 1.36 亿参数。

### 1.5 参数量估算

| 组件 | 计算方式 | 参数量 |
|------|---------|--------|
| Embedding | 151936 × 896 | ≈ 136M |
| 24层 Attention (Q/K/V/O) | 24 × (896×896 + 896×128×2 + 896×896) | ≈ 53M |
| 24层 FFN (gate/up/down) | 24 × (896×4864×3) | ≈ 313M |
| RMSNorm 等 | 49 × 896 | ≈ 0.04M |
| LM Head | 与 Embedding 共享，不额外计算 | 0 |
| **总计** | | **≈ 494M ≈ 0.5B** |

## 第二章：SwiGLU FFN —— gate、up、down 三兄弟

### 2.1 先理解 FFN 是干什么的

Transformer 每一层有两个核心模块：

- **注意力（Attention）**：让每个 token "看到"其他 token，捕捉词与词之间的关系
- **FFN（前馈网络）**：对每个 token **独立地**做一次"深度思考"，提取更高级的特征

打个比方：注意力是"开会讨论"，FFN 是"回去独立思考消化"。

### 2.2 传统 FFN（两层线性变换）

最早的 Transformer FFN 很简单：

```
FFN(x) = ReLU(x × W1) × W2

x: [896维]  →  W1放大  →  [4864维]  →  ReLU激活  →  W2缩小  →  [896维]
             "展开思考"                              "压缩总结"
```

就两步：先放大维度（让模型有更大的"思考空间"），再缩小回来。

### 2.3 Qwen 用的 SwiGLU FFN（三个投影矩阵）

Qwen 用了更先进的 SwiGLU 结构，把 W1 拆成了两个矩阵，多了一个"门控"机制：

```python
# 伪代码
def ffn(x):
    gate = silu(x @ W_gate)   # gate_proj: 896 → 4864，再过 SiLU 激活
    up   = x @ W_up           # up_proj:   896 → 4864，不过激活函数
    down = (gate * up) @ W_down  # 逐元素相乘后，down_proj: 4864 → 896
    return down
```

用图来看：

```
输入 x [896维]
    │
    ├──── gate_proj ──→ [4864维] ──→ SiLU激活 ──→ gate [4864维]
    │                                                    │
    │                                                    × (逐元素相乘)
    │                                                    │
    └──── up_proj ───→ [4864维] ─────────────────→ up [4864维]
                                                         │
                                                    down_proj
                                                         │
                                                         ▼
                                                  输出 [896维]
```

### 2.4 三个矩阵各自的角色

| 矩阵 | 尺寸 | 作用 | 类比 |
|------|------|------|------|
| gate_proj | 896→4864 | "门控"，决定哪些信息**要保留** | 筛选官：这条信息重要吗？ |
| up_proj | 896→4864 | "候选"，提取所有可能有用的特征 | 候选池：把所有信息都准备好 |
| down_proj | 4864→896 | "压缩"，把结果映射回原始维度 | 总结员：把精华浓缩回去 |

### 2.5 gate 的关键作用

gate 经过 SiLU 激活后，值在 0~正数之间。和 up 逐元素相乘时：

- gate 值接近 0 → 对应位置的信息被"关掉"（过滤掉不重要的）
- gate 值较大 → 对应位置的信息被"放大"（保留重要的）

```
举例（简化为4维）：
  gate = [0.9, 0.01, 0.8, 0.02]    ← "第1、3维重要，第2、4维不重要"
  up   = [3.0, 2.0,  1.5, 4.0]     ← 候选特征
  gate × up = [2.7, 0.02, 1.2, 0.08]  ← 不重要的被压到接近0了
```

### 2.6 SiLU 激活函数

```
SiLU(x) = x × sigmoid(x)

  sigmoid(x) 把值压到 0~1 之间
  再乘以 x 本身

  特点：平滑、允许负值通过（比 ReLU 好），梯度流动更顺畅
```

```
        SiLU 函数图像：
  y │        ╱
    │       ╱
    │      ╱
  0 │─────╱──────────
    │   ╱
-0.3│──╱
    │╱
    └──────────────→ x
   -4  -2   0   2   4
```

对比 ReLU：ReLU 把所有负值直接变成 0（一刀切），SiLU 允许小的负值通过，信息保留更完整。

### 2.7 为什么 SwiGLU 比传统 FFN 好？

传统 FFN 用 ReLU，简单粗暴地把负值全部变成 0，丢失了很多信息。

SwiGLU 的门控机制更精细 —— 它让模型**自己学会**哪些特征该保留、哪些该丢弃，表达能力更强。Google 的论文实验证明，同等参数量下 SwiGLU 效果显著优于传统 FFN。

这也解释了为什么 `intermediate_size=4864` 而不是常见的 `4×hidden_size=3584`：SwiGLU 有三个矩阵（比传统 FFN 多一个），为了保持总参数量相近，中间维度做了调整。

## 第三章：RMSNorm —— 训练的稳定器

### 3.1 为什么需要归一化？

神经网络训练时，每一层的输出数值范围会不断变化。经过 24 层 Transformer 后，数值可能变得极大或极小：

```
没有归一化：
  第1层输出:  [0.5, -0.3, 0.8, ...]        ← 正常
  第12层输出: [150, -230, 480, ...]         ← 数值爆炸了！
  第24层输出: [99999, -88888, ...]          ← 完全失控

有归一化：
  第1层输出:  [0.5, -0.3, 0.8, ...]  → 归一化 → [0.4, -0.2, 0.6, ...]
  第12层输出: [1.2, -0.8, 1.5, ...]  → 归一化 → [0.5, -0.3, 0.6, ...]
  第24层输出: [0.9, -0.6, 1.1, ...]  → 归一化 → [0.4, -0.3, 0.5, ...]
  ↑ 每层输出都被"拉回"到稳定范围
```

归一化就是在每一层之后（或之前），把数值"拉回"到一个稳定的范围，防止训练崩溃。

### 3.2 LayerNorm（前辈）

早期 Transformer 用的是 LayerNorm：

```
LayerNorm(x) = (x - mean) / sqrt(variance + eps) × γ

步骤：
  1. 计算均值 mean
  2. 计算方差 variance
  3. 减去均值（中心化）
  4. 除以标准差（缩放到单位方差）
  5. 乘以可学习参数 γ（让模型自己调整缩放）
```

### 3.3 RMSNorm（简化版，Qwen 使用）

RMSNorm 去掉了"减均值"这一步，只保留缩放：

```
RMSNorm(x) = x / sqrt(mean(x²) + eps) × γ

步骤：
  1. 计算 x 每个元素的平方的均值 → 得到 RMS²
  2. 开根号得到 RMS（均方根）
  3. 除以 RMS（缩放到稳定范围）
  4. 乘以可学习参数 γ
```

### 3.4 用具体数字算一遍

```
输入向量 x = [3.0, -1.0, 2.0, -4.0]   （实际是896维，这里简化为4维）

第1步：计算 x² 的均值
  x² = [9.0, 1.0, 4.0, 16.0]
  mean(x²) = (9+1+4+16)/4 = 7.5

第2步：计算 RMS
  RMS = sqrt(7.5 + 1e-6) ≈ 2.739

第3步：除以 RMS
  x / RMS = [3.0/2.739, -1.0/2.739, 2.0/2.739, -4.0/2.739]
          = [1.095, -0.365, 0.730, -1.461]
  ↑ 数值被缩放到了稳定范围！

第4步：乘以可学习参数 γ（初始值通常为全1）
  假设 γ = [1.0, 1.0, 1.0, 1.0]
  输出 = [1.095, -0.365, 0.730, -1.461]
```

### 3.5 RMSNorm vs LayerNorm 对比

| 对比 | LayerNorm | RMSNorm |
|------|-----------|---------|
| 计算步骤 | 减均值 + 除标准差 | 只除 RMS |
| 计算量 | 需要算 mean 和 variance | 只算 mean(x²) |
| 速度 | 较慢 | **快约 10-15%** |
| 效果 | 好 | **几乎一样好** |
| 使用者 | 早期 Transformer、BERT | Qwen、LLaMA、DeepSeek |

研究发现，LayerNorm 中"减均值"这一步对最终效果贡献很小，去掉它可以省计算量，效果基本不变。所以现在主流大模型都用 RMSNorm。

### 3.6 RMSNorm 在 Qwen 中的位置

```
每个 Transformer Block 内部（Pre-Norm 结构）：

  输入 x
    │
    ▼
  RMSNorm ← 注意力之前做一次归一化
    │
    ▼
  Self-Attention
    │
    ▼
  x + attention_output  ← 残差连接
    │
    ▼
  RMSNorm ← FFN 之前再做一次归一化
    │
    ▼
  SwiGLU FFN
    │
    ▼
  x + ffn_output  ← 残差连接
```

config 中的 `rms_norm_eps=1e-6` 就是公式里的 eps，防止除以 0。

24 层 Transformer 一共有 **24×2 + 1 = 49 个 RMSNorm**（每层 2 个 + 最后输出前 1 个）。每个 RMSNorm 只有 896 个可学习参数 γ，总共约 4.4 万参数，非常轻量。

### 3.7 Pre-Norm vs Post-Norm

Qwen 用的是 **Pre-Norm**（先归一化再计算），而不是原始 Transformer 的 Post-Norm（先计算再归一化）：

```
Post-Norm（原始Transformer，已过时）：
  x → Attention → Add(x) → LayerNorm → FFN → Add → LayerNorm
                            ↑ 归一化在后面

Pre-Norm（Qwen/LLaMA等现代模型）：
  x → RMSNorm → Attention → Add(x) → RMSNorm → FFN → Add
      ↑ 归一化在前面
```

Pre-Norm 的优势：梯度流动更顺畅，训练更稳定，尤其是在层数很深（24层以上）的时候。

## 总结：三个问题的关系

```
Transformer Block（×24层）
│
├── RMSNorm ← 第三章：稳定数值，防止训练崩溃
│     │
│     ▼
├── GQA Attention ← 第一章：让 token 之间交流信息
│     │
│     ▼
├── 残差连接
│     │
│     ▼
├── RMSNorm ← 第三章
│     │
│     ▼
├── SwiGLU FFN ← 第二章：gate/up/down 三兄弟，独立深度思考
│     │         gate 负责筛选，up 负责候选，down 负责压缩
│     ▼
└── 残差连接
```

这三个组件协同工作：RMSNorm 保证数值稳定，Attention 负责"交流"，SwiGLU FFN 负责"思考"。24 层堆叠下来，模型就具备了强大的语言理解和生成能力。

## 第四章：Batch Size、梯度累积与多卡训练 —— 显存到底怎么算？

> 这一章解决一个很多人搞不清的问题：batch size、梯度累积、多卡训练之间到底是什么关系？
> 对显存的影响分别是什么？我们用最直观的方式一步步拆解。

### 4.1 先搞清楚一个核心概念：一次"参数更新"需要多少样本？

训练的本质是：**看一批样本 → 算梯度 → 更新参数**。

这"一批样本"的数量，就是 **全局 Batch Size（Global Batch Size）**。它由三个因素决定：

```
全局 Batch Size = per_device_train_batch_size × gradient_accumulation_steps × GPU数量
```

以 `qwen_pt.py` 为例：

```python
per_device_train_batch_size = 24    # 每张 GPU 每次吃 24 个样本
gradient_accumulation_steps = 16    # 累积 16 次
# 假设 1 张 GPU
```

```
全局 Batch Size = 24 × 16 × 1 = 384
意思是：模型每看完 384 个样本，才真正更新一次参数
```

### 4.2 为什么 Batch Size 很重要？

```
Batch Size 太小（比如 1）：
  ┌─────────────────────────────────────────────┐
  │ 只看 1 个样本就更新参数                        │
  │ → 这个样本可能是个"奇葩"（噪声大）             │
  │ → 参数更新方向不稳定，像喝醉酒走路              │
  │                                               │
  │   最优解 ★                                    │
  │          ↗ ↙ ↘ ↖ ↗ ↙  ← 到处乱走            │
  └─────────────────────────────────────────────┘

Batch Size 合适（比如 384）：
  ┌─────────────────────────────────────────────┐
  │ 看 384 个样本取平均再更新                      │
  │ → 噪声被平均掉了，方向更准确                   │
  │ → 稳步走向最优解                               │
  │                                               │
  │   最优解 ★                                    │
  │        ↙ ↙ ↙ ↙ ↙  ← 稳定前进                │
  └─────────────────────────────────────────────┘

Batch Size 太大（比如 10000）：
  ┌─────────────────────────────────────────────┐
  │ 看太多样本才更新一次                           │
  │ → 更新次数太少，训练太慢                       │
  │ → 而且可能陷入"尖锐"的局部最优，泛化能力差      │
  └─────────────────────────────────────────────┘
```

### 4.3 显存里到底装了什么？

要理解 batch size 对显存的影响，先搞清楚 GPU 显存里装了哪些东西：

```
┌──────────────────────────────────────────────────────────┐
│                    GPU 显存分配                            │
│                                                          │
│  ① 模型参数（固定开销，跟 batch size 无关）                │
│     Qwen2.5-0.5B，BF16 精度                              │
│     494M × 2字节 ≈ 1 GB                                  │
│                                                          │
│  ② 优化器状态（固定开销，跟 batch size 无关）              │
│     AdamW 为每个参数维护 2 个状态（动量 m 和方差 v）        │
│     494M × 2 × 4字节(FP32) ≈ 4 GB                       │
│                                                          │
│  ③ 梯度（固定开销，跟 batch size 无关）                    │
│     每个参数一个梯度值                                     │
│     494M × 2字节 ≈ 1 GB                                  │
│                                                          │
│  ④ 激活值（⚠️ 跟 batch size 成正比！这是关键！）          │
│     前向传播的中间结果，反向传播时需要用                     │
│     每个样本都要保存一份                                   │
│     batch_size=1 时约 0.5 GB                              │
│     batch_size=24 时约 12 GB                              │
│                                                          │
│  ⑤ 临时缓冲区                                            │
│     计算过程中的临时变量，约 0.5-1 GB                      │
│                                                          │
├──────────────────────────────────────────────────────────┤
│  总计（batch_size=24，无梯度检查点）：                      │
│  1 + 4 + 1 + 12 + 1 = 约 19 GB                          │
│                                                          │
│  总计（batch_size=24，有梯度检查点）：                      │
│  1 + 4 + 1 + 3 + 1 = 约 10 GB   ← 激活值大幅减少         │
└──────────────────────────────────────────────────────────┘
```

**关键结论：**

| 显存组成 | 大小 | 受 batch size 影响？ |
|---------|------|---------------------|
| 模型参数 | ~1 GB | ❌ 不受影响 |
| 优化器状态 | ~4 GB | ❌ 不受影响 |
| 梯度 | ~1 GB | ❌ 不受影响 |
| **激活值** | **变化很大** | **✅ 正比于 batch size** |
| 临时缓冲区 | ~1 GB | 略有影响 |

**所以：batch size 越大，激活值越多，显存占用越大。这就是为什么显存不够时要减小 batch size。**

### 4.4 梯度累积 —— 穷人的大 Batch

问题来了：我们想要大 batch size 的稳定训练效果，但显存放不下怎么办？

**梯度累积就是解决方案。**

核心思想：把一个大 batch 拆成多个小 batch，分多次算梯度，累加起来，最后一起更新参数。

```
═══════════════════════════════════════════════════════════
  不用梯度累积（batch_size=384，需要巨大显存）
═══════════════════════════════════════════════════════════

  一次性把 384 个样本全部送入 GPU：
  ┌─────────────────────────────────────────────────┐
  │  GPU 显存                                        │
  │  [样本1][样本2][样本3]...[样本384]                │
  │  ← 384个样本的激活值全部在显存里，放不下！→        │
  └─────────────────────────────────────────────────┘
  → 计算梯度 → 更新参数 ✓


═══════════════════════════════════════════════════════════
  用梯度累积（batch_size=24, accumulation=16）
═══════════════���═══════════════════════════════════════════

  第1次：送入 24 个样本
  ┌──────────────────────┐
  │  GPU 显存              │
  │  [样本1]...[样本24]    │  ← 只需要放 24 个样本，显存够用！
  └──────────────────────┘
  → 计算梯度 → 梯度存起来（不更新参数）→ 释放激活值

  第2次：送入下一批 24 个样本
  ┌──────────────────────┐
  │  GPU 显存              │
  │  [样本25]...[样本48]   │
  └──────────────────────┘
  → 计算梯度 → 累加到之前的梯度上 → 释放激活值

  ... 重复 16 次 ...

  第16次：送入最后 24 个样本
  ┌──────────────────────┐
  │  GPU 显存              │
  │  [样本361]...[样本384] │
  └──────────────────────┘
  → 计算梯度 → 累加 → 16次梯度累加完毕 → 更新参数 ✓
```

**效果完全等价于 batch_size=384，但显存只需要放 24 个样本！**

代价是什么？**训练速度变慢**。因为本来一次前向+反向就搞定的事，现在要做 16 次。但这是值得的——没有梯度累积，你根本跑不起来。

### 4.5 梯度累积对显存的影响

```
                    显存占用对比
  
  方案A：batch_size=384, 无累积
  ┌──────────────────────────────────────────┐
  │ 模型1G │ 优化器4G │ 梯度1G │ 激活值~192G │  ← 根本放不下！
  └──────────────────────────────────────────┘
  
  方案B：batch_size=24, 累积16次
  ┌──────────────────────────┐
  │ 模型1G │优化器4G│梯度1G│激活12G│  ← 约 19G，一张卡能放下
  └──────────────────────────┘
  
  两种方案的全局 Batch Size 都是 384，训练效果一样！
```

**梯度累积不增加显存**，因为：
- 每个小 batch 算完梯度后，激活值就释放了
- 梯度本身很小（跟模型参数一样大，~1GB），累加不占额外空间
- 显存峰值 = 一个小 batch 的开销

### 4.6 单卡 vs 多卡 —— 数据并行（Data Parallel）

多卡训练最常见的方式是 **数据并行（Data Parallel, DP）**：每张 GPU 拿到不同的数据，各自算梯度，然后汇总。

```
═══════════════════════════════════════════════════════════
  单卡训练（1 × GPU）
═══════════════════════════════════════════════════════════

  ┌─────────────────────────────┐
  │  GPU 0                       │
  │  完整模型副本                 │
  │  batch_size=24               │
  │  累积16次                    │
  │  全局 Batch = 24×16×1 = 384  │
  └─────────────────────────────┘
  
  每次参数更新需要：24×16 = 384 次前向+反向传播
  全部由 1 张卡完成 → 慢


═══════════════════════════════════════════════════════════
  4卡数据并行（4 × GPU）
═══════════════════════════════════════════════════════════

  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
  │  GPU 0        │ │  GPU 1        │ │  GPU 2        │ │  GPU 3        │
  │  完整模型副本  │ │  完整模型副本  │ │  完整模型副本  │ │  完整模型副本  │
  │  batch=24     │ │  batch=24     │ │  batch=24     │ │  batch=24     │
  │  累积16次     │ │  累积16次     │ │  累积16次     │ │  累积16次     │
  └──────┬───────┘ └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
         │                │                │                │
         └────────────────┴────────────────┴────────────────┘
                                  │
                          AllReduce 汇总梯度
                          （4张卡的梯度取平均）
                                  │
                          全局 Batch = 24×16×4 = 1536
                          更新参数（4张卡同步更新）
```

**关键理解：**

| 对比 | 单卡 | 4卡数据并行 |
|------|------|------------|
| 每张卡的显存占用 | ~19 GB | ~19 GB（**一样！**） |
| 全局 Batch Size | 24×16×1 = 384 | 24×16×4 = 1536 |
| 每次更新的计算量 | 384 次前向反向 | 每卡 384 次，但 4 卡并行 |
| 训练速度 | 1× | **接近 4×**（有通信开销） |

**多卡数据并行不省显存！每张卡都要放一份完整的模型 + 优化器 + 梯度 + 激活值。**

多卡的好处是**速度快**（多张卡同时算）和**全局 Batch Size 更大**（更稳定）。

### 4.7 如果想多卡省显存呢？—— DeepSpeed ZeRO

数据并行的问题：每张卡都存一份完整的模型参数 + 优化器状态，太浪费了。

**DeepSpeed ZeRO** 的思路：把这些东西**切开分给不同的卡**。

```
═══════════════════════════════════════════════════════════
  普通数据并行（每张卡都存全量）
═══════════════════════════════════════════════════════════

  GPU 0                    GPU 1
  ┌──────────────────┐    ┌──────────────────┐
  │ 全部模型参数 1GB  │    │ 全部模型参数 1GB  │  ← 重复存储！
  │ 全部优化器  4GB   │    │ 全部优化器  4GB   │  ← 重复存储！
  │ 全部梯度    1GB   │    │ 全部梯度    1GB   │  ← 重复存储！
  │ 激活值      12GB  │    │ 激活值      12GB  │
  │ 总计: ~19GB       │    │ 总计: ~19GB       │
  └──────────────────┘    └──────────────────┘


═══════════════════════════════════════════════════════════
  DeepSpeed ZeRO Stage 2（切分优化器和梯度）
═══════════════════════════════════════════════════════════

  GPU 0                    GPU 1
  ┌──────────────────┐    ┌──────────────────┐
  │ 全部模型参数 1GB  │    │ 全部模型参数 1GB  │
  │ 一半优化器  2GB   │    │ 另一半优化器 2GB  │  ← 各存一半！
  │ 一半梯度   0.5GB  │    │ 另一半梯度  0.5GB │  ← 各存一半！
  │ 激活值      12GB  │    │ 激活值      12GB  │
  │ 总计: ~16GB       │    │ 总计: ~16GB       │
  └──────────────────┘    └──────────────────┘
  省了约 3GB/卡


═══════════════════════════════════════════════════════════
  DeepSpeed ZeRO Stage 3（全部切分）
═══════════════════════════════════════════════════════════

  GPU 0                    GPU 1
  ┌──────────────────┐    ┌──────────────────┐
  │ 一半模型   0.5GB  │    │ 另一半模型  0.5GB │  ← 各存一半！
  │ 一半优化器  2GB   │    │ 另一半优化器 2GB  │  ← 各存一半！
  │ 一半梯度   0.5GB  │    │ 另一半梯度  0.5GB │  ← 各存一半！
  │ 激活值      12GB  │    │ 激活值      12GB  │
  │ 总计: ~15GB       │    │ 总计: ~15GB       │
  └──────────────────┘    └──────────────────┘
  省了约 4GB/卡（卡越多省越多）
```

代价：卡之间需要频繁通信（"我需要你那部分参数，传给我"），通信开销增大，训练速度略降。

### 4.10 常见误区澄清

**误区1："梯度累积 = 显存翻倍"**

❌ 错。梯度累积**不增加显存**。显存峰值只取决于单次前向传播的 batch_size。

**误区2："多卡训练能省显存"**

❌ 错（普通数据并行）。每张卡都要存完整模型，显存跟单卡一样。想省显存要用 DeepSpeed ZeRO。

**误区3："全局 Batch Size 越大越好"**

❌ 错。太大的 batch size 会导致：
- 每个 epoch 的参数更新次数减少（学得不够细）
- 可能收敛到"尖锐"的局部最优（泛化差）
- 通常 256~2048 是比较好的范围

**误区4："gradient_accumulation_steps 越大训练越快"**

❌ 错。恰恰相反，累积步数越大，每次参数更新需要的前向反向次数越多，**训练越慢**。它的作用是在不增加显存的前提下模拟大 batch，是一种"用时间换效果"的策略。

### 4.11 实际调参建议

```
第1步：先确定你的显存能放多大的 per_device_train_batch_size
       从小到大试：1 → 2 → 4 → 8 → 16 → 24 → 32
       直到 OOM（显存不足），退回上一个值

第2步：确定你想要的全局 Batch Size（通常 256~1024）

第3步：反算 gradient_accumulation_steps
       accumulation = 目标全局Batch / (per_device_batch × GPU数)
       
       例如：目标 512，per_device=8，2张卡
       accumulation = 512 / (8 × 2) = 32

第4步：如果 accumulation 算出来太大（>32），说明单卡 batch 太小
       → 考虑开梯度检查点（gradient_checkpointing=True）
       → 或者用 DeepSpeed ZeRO 省显存
       → 或者减小 max_seq_length
```
